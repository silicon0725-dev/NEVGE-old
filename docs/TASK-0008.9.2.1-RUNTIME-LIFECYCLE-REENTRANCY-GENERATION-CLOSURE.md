## Hook reentrancy policy

Lifecycle Hooks remain local Provider callbacks. During a Hook, the current Runtime semantic graph is in a partially observed lifecycle transition and is therefore not a legal synchronous mutation boundary.

Frozen policy:

```text
Lifecycle Hook reads Runtime state
        ↓
Hook may manage provider-owned external resources
        ↓
Hook requests synchronous Runtime semantic mutation
        ↓
RUNTIME_LIFECYCLE_REENTRANT_MUTATION
        ↓
lifecycle:error
        ↓
Original lifecycle transition completes
```

The policy is machine-readable as:

```text
hookReentrancyPolicy:
reject-synchronous-runtime-semantic-mutation
```

The guard covers Graph mutation entry points, public Runtime Node mutations, restricted type registration that can reify nodes, internal Scene synchronization and direct local Node/Component mutation helpers.

Examples rejected during a Hook include:

```text
createNode
destroyNode
setNodeEnabled
setParent
detachNode
addComponent
removeComponent
patchComponentData
component.patchData
importState
synchronizeScenes
```

The Hook exception remains non-vetoing. It is isolated and reported as `lifecycle:error`; the original transition continues to a legal final state.

This version does not add an implicit deferred mutation queue. Deferral, ordering and rollback belong to the future Command/Transaction contract.

## Runtime generation

Lifecycle event order is identified by:

```text
(runtimeGeneration, sequence)
```

Rules:

```text
Initial committed Runtime Graph:
runtimeGeneration = 1

Successful Runtime Graph replacement/import:
runtimeGeneration += 1
sequence = 0
publish runtime:replaced as sequence 1

Failed import:
runtimeGeneration unchanged
sequence unchanged
```

The committed replacement event is:

```js
{
    type: 'runtime:replaced',
    lifecycleContractVersion: '1',
    runtimeGeneration: 4,
    previousRuntimeGeneration: 3,
    sequence: 1,
    reason: 'state-import'
}
```

Shadow Graph construction traces are discarded at commit. They are not exposed as if they had occurred in the committed Runtime generation.

`runtimeGeneration` is Runtime-derived diagnostic identity. It is included in lifecycle events, lifecycle errors, Runtime status, Debug Snapshot and state-import notifications. It is never persisted and does not replace stable `NodeId`, `SceneId`, `BindingId` or resource identity.

## Observer diagnostics

Runtime observer diagnostics are split into:

```text
graphListenerErrorCount
    RuntimeNodeGraph internal listener failures

observerErrorCount
    runtimeNodeModel.subscribe() public observer failures

listenerErrorCount
    graphListenerErrorCount + observerErrorCount
```

A failing public observer:

- increments `observerErrorCount`;
- contributes to `listenerErrorCount`;
- does not interrupt other observers;
- does not veto or roll back the mutation;
- is not re-broadcast as another event, preventing recursive observer error storms.

## Same-state transitions

A Runtime Node or Component `_transition(nextState, ...)` call whose state already equals `nextState` is a pure no-op:

```text
return false
no Hook
no lifecycle event
no Trace append
no sequence increment
```

The machine transition table contains no self-loop. Calling `assertLifecycleTransition()` directly with a same-state pair throws `RUNTIME_LIFECYCLE_TRANSITION_INVALID`.

The normal first-attach path cannot skip Ready:

```text
Created → Attached → Ready → Active / Disabled
```

A previously Ready Node may move from Attached to Active/Disabled only during Reparent reattachment. This is represented as a conditional machine-readable transition requiring `readyInvoked: true`; it does not invoke or emit Ready again.

## Detach domains

Two lifecycle domains are explicitly distinct:

```text
Node Detach
= Node and Parent/Scene hierarchy relationship removed

Component Detach
= Component and Owner Node ownership relationship removed
```

Therefore `detachNode(nodeId)`:

- disables the Node and owned Components;
- removes the Node parent relationship;
- keeps every Component owned by the detached Node;
- does not emit `component:detach`;
- does not change `component.ownerId`.

`component:detach` occurs only when ownership is removed, such as `removeComponent`, Component replacement or Node destruction.
