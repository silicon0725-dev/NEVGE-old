# Task 0008.7.2.1 — Sprite Tree Ownership Hotfix

## Problem

0008.7.2 exposed two parallel editor representations for the same Scratch Sprite:

- the Runtime `ngvge.scratch-sprite-node` adapter node;
- the legacy `project-nodes` Scratch target node.

The legacy node database also retained its previous state when a scene snapshot omitted the node-tree project section. This allowed compatibility children from one scene to be rebound to a target in another scene. When a Scratch target was deleted, its compatibility children were promoted to the root instead of being deleted with the target-owned subtree.

## Fix

- Project Explorer uses the adapter node as the single visible Sprite row when a stable binding is active.
- Legacy compatibility children are rendered beneath that adapter node instead of beneath a second `Sprite` row.
- Selecting the unified row selects both the Runtime Node and the bound Scratch target.
- Scene-local project sections can opt into `clearOnMissing`; the compatibility node tree uses this contract.
- Loading a snapshot without node-tree data resets the compatibility tree for the newly loaded scene.
- Removing a Scratch target recursively removes its target-backed compatibility subtree.
- The adapter listens to both Runtime `TARGETS_UPDATE` and public VM `targetsUpdate` events; duplicate event turns are coalesced.

## Version

Scene System: `0.7.2.1`

## Existing orphan note

Compatibility nodes already promoted to the scene root by an older build have lost their original target ownership. The hotfix does not automatically delete those ambiguous nodes. They can be removed manually once; subsequent Sprite deletions use recursive target ownership cleanup.
