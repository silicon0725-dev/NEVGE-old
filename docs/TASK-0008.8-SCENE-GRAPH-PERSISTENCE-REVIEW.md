# TASK-0008.8｜Scene Graph Persistence Review

Status: `Completed`

Depends on: `0008.7.3 Scratch Adapter Boundary Stabilization`

Scene System version: `0.8.0`

## Objective

Review and harden the complete persistence boundary shared by the Scene Data Model, Runtime Node Model, Scratch Sprite Adapter and Scene Snapshot Serializer.

This task does not introduce the final ARC-C001 Conformance Suite. It establishes the local Scene System persistence contract required before `0008.9 Runtime Node Model Freeze`.

## Persistence ownership

```text
Scene System project data
├── Scene records
├── Runtime Node persistent records
└── Scratch Binding sidecar

Runtime-only state
├── Scratch Target objects and target.id
├── Runtime lifecycle state
├── activeInHierarchy / ready / owner caches
├── listeners, timers and promises
└── prepared ZIP and cache objects
```

Only the first group may enter module project storage.

## Implemented changes

### Strict persistent data contract

`src/lib/persistence/persistent-data.js` validates the complete object graph before cloning or writing it. It accepts primitives, arrays and plain objects and rejects:

- `Function`, `Promise`-like class instances, `Symbol` and `BigInt`;
- `undefined` values nested in persistent data;
- `NaN`, positive infinity and negative infinity;
- class instances and other non-plain objects;
- accessor and non-enumerable properties;
- custom array properties and sparse arrays;
- circular references.

Persistence no longer treats `JSON.stringify()` as a validator. Invalid values fail with structured paths instead of being silently removed or converted.

### Scene project validation

`SceneDataModelService.writeProject()` now performs:

```text
Persistent plain-data validation
→ scene project normalization
→ Scene Schema validation
→ atomic module-data write
```

An invalid project throws `SCENE_PERSISTENT_DATA_INVALID` or `SCENE_DATA_VALIDATION_FAILED` before the stored project changes.

### Runtime Node persistence protection

Runtime Node metadata, source descriptors, component data and opaque provider payloads now use the strict persistent clone contract.

A stored Runtime Node state with a newer version enters persistence read-only mode:

```text
persistenceReadOnly: true
storedStateVersion: <future version>
```

Mutations fail with `RUNTIME_NODE_STATE_READ_ONLY`, and `persistState()` does not overwrite the newer payload.

The Runtime Node capability also exposes `validatePersistentState(snapshot)` for persistence audits.

### Scratch Binding persistence

The semantic `ngvge.scratch-target-binding` component no longer stores the runtime-derived `lifecycle` field. Neither component records nor the sidecar store volatile `targetRuntimeId` values.

Sidecar validation checks:

- persistent plain-data validity;
- supported schema version;
- stable `BindingId` and `NodeId` values;
- duplicate identities across all scenes;
- references to deleted scenes;
- accidental persistence of volatile Target IDs.

Deleting a Scene prunes its `scratchSpriteBindings.scenes[sceneId]` record.

### Restore rollback

Before a destructive Scene snapshot restore, the serializer attempts to capture an in-memory rollback point from the currently loaded Scratch project.

```text
Prepare target snapshot
→ capture current-project rollback point
→ stop runtime
→ deserialize target snapshot
→ publish Project Loaded
```

If deserialization or project-loaded handling fails after destructive restore begins:

```text
restore failure
→ deserialize rollback point
→ publish restore-rollback / restore-rollback-error
→ rethrow original failure with error.rollback
```

No rollback archive is persisted in the project. It exists only for the duration of the restore transaction.

### Persistence Review capability

Scene System now provides:

```text
ngvge.scene-persistence-review@1
```

Public operations:

```js
const review = modules.getCapability('ngvge.scene-persistence-review');
review.audit();
review.assertValid();
review.getLastReport();
```

The review detects invalid plain data, Scene Schema errors, invalid Runtime Node snapshots, runtime-derived fields in persistent records, Scratch Binding leakage and snapshot-to-scene identity mismatches.

## Persistent identity reconstruction

The validation flow explicitly covers:

```text
Save project data
→ dispose Runtime Node Model and Scratch Adapter
→ recreate Scratch Target with a different target.id
→ recreate Runtime Node Model and Adapter
→ restore the original NodeId and BindingId
```

Active and offline Scene bindings retain stable identities. The new Scratch Target runtime ID remains an Adapter-only binding detail.
