# WS-7 | NGVGE Agent Workspace Integration

Status: `COMPLETE / VERIFIED`

Baseline: WS-6 verified local commit `0bfdddc`.

## 1. Purpose

WS-7 introduces the NGVGE Agent as a governed Workspace Tool. It does not reuse the Legacy 02Agent application/window/runtime authority.

The product path is:

```text
ToolRegistry
  -> WindowModel
  -> WindowManager
  -> Workspace Agent
  -> ChangeSet
  -> explicit Review
  -> reviewed Transaction Host
  -> Workspace Node Command Authority
  -> Engine Protocol / compatibility authority
  -> Commit or Rollback
```

The Agent is a proposal/review surface. It is not a direct VM, renderer, Scratch target, project, credential, or window authority.

## 3. Workspace integration

The Agent is registered as a first-party singleton ToolDefinition and receives a managed WindowDefinition. It is default-hidden and is not a default-pinned Dock item.

Launchpad discovery remains registry-driven. The Launchpad does not contain an Agent-specific tool list.

The Agent window is owned by WindowManager. The compatibility `DraggableWindow` persistence writer remains disabled; WS-4 WindowManager persistence is canonical.

## 4. New Agent is not Legacy 02Agent

The new Workspace Agent imports no Legacy 02Agent code and does not inherit its portal, bridge, or runtime mutation behavior.

Legacy 02Agent remains under the LSC containment contract with read-only mutation mode. WS-7 does not weaken that quarantine.

New Agent production sources do not use:

```text

window.vm
raw Scratch VM handles
renderer private handles
Scratch target/runtime identity

Agent-owned localStorage/sessionStorage

```

## 5. Agent context boundary

The runtime receives current context only through the shared WorkspaceNodeCommandHost query boundary.

The safe projection contains stable semantic information such as:

```text
NodeId
name
typeId
parentId
enabled
domain
```

The UI explicitly declares what the Agent can and cannot see. Raw VM objects, renderer internals, Scratch target/runtime identity, credential contents, and unreviewed mutation authority are outside the Agent context contract.

## 6. ChangeSet v1

A proposal is normalized into a portable versioned ChangeSet before review.

WS-7 v1 supports only reversible Workspace Node commands:

```text
CreateNode
DuplicateNode
PatchNode
ReparentNode
```

`DestroyNode` is intentionally excluded from ChangeSet v1 because the current authority boundary cannot guarantee an exact general reconstruction/rollback contract.

ChangeSet payload validation recursively rejects backend/private identity including VM, renderer, target, targetId, runtimeId, scratchTargetId, editingTargetId, extensionManager, and backendId.

## 7. Review is a hard authorization boundary

The Workspace Node Host accepts Agent mutations only when an internal reviewed-transaction authorization token is present.

A normal public Workspace Node client cannot be created for `ngvge.tool.agent`. The privileged reviewed client is created only by the Agent Transaction Host.

Therefore this path is invalid:

```text
Agent UI
  -> WorkspaceNodeCommandHost mutation
```

The valid path is:

```text
Agent proposal
  -> ChangeSet(PROPOSED)
  -> user Apply
  -> ChangeSet(APPROVED)
  -> Agent Transaction Host
  -> private reviewed authorization
  -> Workspace Node Command Host
```

The private review token does not appear in ChangeSet DTOs or Agent UI state.

## 8. Transaction and compensation

Rollback commands are generated by the trusted Transaction Host from actual pre-operation snapshots/results. They are never supplied by the AI proposal.

Compensation rules:

```text
CreateNode    -> Destroy newly created NodeId
DuplicateNode -> Destroy duplicated NodeId
PatchNode     -> trusted inverse patch from pre-snapshot
ReparentNode  -> restore previous parentId
```

If an operation later in a ChangeSet fails, already applied operations are compensated in reverse order.

A committed transaction is retained in runtime undo history and can be manually rolled back. Manual rollback failure becomes an explicit `rollback-failed` transaction state.

## 9. Fail-closed reversibility

WS-7 does not claim transactional behavior where exact compensation is unavailable.

Examples:

- a Project Node property patch that introduces a previously nonexistent property is rejected before apply because the current command boundary cannot delete that property exactly;
- a Runtime Node reparent is rejected if the previous parent cannot be represented as a reversible parent target;
- unsupported patch fields are rejected before execution;
- destructive `DestroyNode` proposals are rejected at ChangeSet normalization.

This is deliberate: fewer supported mutations are preferable to an Apply/Undo UI that is not transactionally truthful.

## 10. Agent UI contract

The Workspace Agent emphasizes:

```text
Current Context
What AI can see
Explicitly unavailable
Proposed Changes
Portable Diff
Review
Apply / Reject
Undo history
Reviewed transactions
```

WS-7 does not implement an independent ChatGPT-clone application shell.

An AI/provider adapter is not an execution authority. Future provider integrations may submit portable proposals through `WorkspaceAgentModel.proposeChangeSet()`, after which the same ChangeSet/review/transaction path applies.

## 11. Persistence

Agent Window geometry/visibility follows the existing WS-4 Workspace persistence path through WindowManager.

ChangeSets, transaction compensation records, selected proposal state, and Undo history are runtime/session state in WS-7 v1. No new Agent localStorage or sessionStorage domain is introduced.

Credentials remain owned by the LSC credential boundary.

## 12. Authority result

WS-7 establishes the following invariant:

> The Agent may propose semantic changes, but only an explicitly reviewed ChangeSet can obtain the private transaction authorization required to reach existing NGVGE command authority. Presentation, model-provider logic, and Legacy Agent code never become mutation authorities.
